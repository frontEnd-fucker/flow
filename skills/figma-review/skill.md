**开始时：**

1. **自动提取 Figma 链接**：
   - 扫描项目中的页面文件（如 `pages/**/*.tsx`, `app/**/*.tsx`, `src/pages/**/*.vue` 等）
   - 从文件头部注释中提取 Figma URL（格式：`https://figma.com/design/:fileKey/:fileName?node-id=1-2`）
   - 注释格式示例：
     ```typescript
     /**
      * Figma: https://figma.com/design/AbCdEf123/ProjectName?node-id=1-2
      * 或
      * @figma https://figma.com/design/AbCdEf123/ProjectName?node-id=1-2
      */
     ```

2. **如果没有找到 Figma 链接**：
   - 尝试从 `docs/requirements.md` 中提取
   - 如果仍未找到，询问用户提供 Figma 文件 URL

### 页面发现流程

**自动发现可比对的页面：**

1. 扫描项目结构，识别所有页面文件
2. 提取每个页面文件头部的 Figma 链接
3. 生成页面列表供用户选择：

```json
{
  "questions": [
    {
      "question": "请选择要进行比对的页面",
      "header": "页面选择",
      "multiSelect": true,
      "options": [
        {"label": "登录页 - pages/login.tsx"},
        {"label": "首页 - pages/index.tsx"},
        {"label": "用户管理 - pages/users.tsx"}
      ]
    }
  ]
}
```

**options 限制**：每个 question 的 options 最多 4 个，超过时需要拆分多个 question。

### 截图比对流程

**对每个选中的页面执行以下步骤：**

#### 1. 获取 Figma 设计截图

**约束：截图应该在整个流程中可用，后续流程不要再对同一个figma节点截图**

使用figma-desktop `get_screenshot` 工具传入正确参数获取 Figma 设计稿截图，传入以下参数：

**参数提取规则：**
- 从页面文件头部注释中的 Figma URL 提取 `fileKey` 和 `nodeId`
- URL 格式：`https://figma.com/design/{fileKey}/{fileName}?node-id={nodeId}`
- `nodeId` 需要把 `-` 替换为 `:`（如 `1-2` → `1:2`）

**示例：**
```typescript
// 页面文件头部注释中的 Figma URL：
// https://figma.com/design/AbCdEf123/ProjectName?node-id=2763-19984

// 提取参数：
// fileKey = "AbCdEf123"
// nodeId = "2763:19984" (注意 - 已替换为 :)
```

**工具调用：**
```json
{
  “fileKey”: “从URL提取的fileKey”,
  “nodeId”: “从URL提取的nodeId（-替换为:）”
}
```

#### 2. 获取实现页面的截图

找到正确的开发服务器端口，如果没有则启动一个，使用 `chrome-devtools-mcp` 的 `take_screenshot` 工具传入正确参数获取实现页面的截图并保存到`/screenshot`文件夹下

**参数说明：**
- `filePath`: 截图保存路径，格式为 `/screenshot/{页面名称}.png`
- `fullPage`: 是否截取全页，设置为 `true`
- 确保页面已加载完成后再截图

**工具调用示例：**
```json
{
  "filePath": "/screenshot/login.png",
  "fullPage": true
}
```

**执行步骤：**
1. 使用 `navigate_page` 导航到本地开发服务器页面（如 `http://localhost:3000/login`）
2. 等待页面完全加载
3. 使用 `take_screenshot` 截取页面截图并保存到 `/screenshot` 目录

完成后宣告用户：“文件已经保存到/screenshot文件夹”

#### 3. 视觉对比检查清单

非常严格地从以下维度对比两张照片，输出详细的差异报告：

| 检查项 | 说明 |
|-------|------|
| **布局** | 元素位置、间距、对齐方式等是否符合设计稿 |
| **组件** | 各个组件的位置以及组件间的间距是否与figma一致|
| **颜色** | 背景色、文字色、按钮色等是否与 Figma 一致 |
| **字体** | 字体族、字号、字重、行高等是否匹配 |
| **尺寸** | 元素宽高、内边距、外边距等是否准确 |
| **图标** | 图标是否一致 |

#### 4. 输出格式

为每个页面对输出如下报告：

```markdown
### 【页面名称】对比结果

**Figma 设计稿：**
[截图路径]

**实现页面：**
[截图路径]

**差异检查：**

| 检查项 | 状态 | 说明 |
|-------|------|------|
| 布局 | ✅ 通过 | 左右间距与设计稿一致 |
| 颜色 | ⚠️ 警告 | 按钮主色使用 `#1890ff`，设计稿为 `#1677ff` |
| 字体 | ❌ 不符 | 标题字号 18px，设计稿为 16px |
| ... | ... | ... |

**修复建议：**
1. 将按钮主色从 `#1890ff` 改为 `#1677ff`
2. 调整标题字号从 18px 改为 16px
```

### 变量提取辅助

如果需要精确的颜色/字体值进行比对，使用 `get_variable_defs` 或 `get_design_context` 工具传入正确参数：

```json
{
  "fileKey": "文件 Key",
  "nodeId": "页面 node-id"
}
```

### 自动修复循环流程

如果发现差异，**无需再询问用户**，启动自动修复循环（最多 5 次）：

#### 循环流程

```
第 1 次比对 → 发现差异 → 自动修复 → 第 2 次比对
     ↓
第 2 次比对 → 发现差异 → 自动修复 → 第 3 次比对
     ↓
第 3 次比对 → 发现差异 → 自动修复 → 第 4 次比对
     ↓
第 4 次比对 → 发现差异 → 自动修复 → 第 5 次比对
     ↓
第 5 次比对 → 仍有差异 → 终止循环 → 生成最终报告交用户决策
```

#### 每次修复后重新比对

**修复步骤：**
1. 根据差异报告生成修复方案
2. 修改对应的代码文件
3. 保存后重新刷新页面
4. **重新执行截图比对流程：**
   - 重新获取 Figma 设计截图（缓存）
   - 重新获取实现页面截图（刷新后）
   - 重新进行视觉对比检查
   - 生成新的差异报告

#### 循环终止条件

- ✅ **无差异**：对比结果通过，所有检查项为 ✅，终止循环
- ⚠️ **达上限**：已完成 5 次修复循环，仍有差异，终止循环
- 🛑 **手动中断**：用户要求停止自动修复

#### 最终报告
**确保修改前和修改后的截图都保存到/screenshot目录**

**情况 1：修复成功（无差异）**
```markdown
## 修复完成报告

**页面：** {页面名称}
**修复轮次：** 3 次
**最终状态：** ✅ 所有检查项通过

**修复历史：**
- 第 1 轮：修复按钮颜色、调整标题字号
- 第 2 轮：修复间距、调整图标大小
- 第 3 轮：微调布局对齐 → 通过
```

**情况 2：达到循环上限（需用户决策）**
```markdown
## 修复报告 - 需用户决策

**页面：** {页面名称}
**修复轮次：** 5 次（已达上限）
**最终状态：** ⚠️ 仍有差异

**剩余问题清单：**
| 检查项 | 状态 | 说明 |
|-------|------|------|
| 颜色 | ⚠️ 警告 | 渐变背景色无法精确匹配 |
| 字体 | ⚠️ 警告 | 特殊字体需要授权 |

**建议决策：**
1. 接受当前差异（推荐）
2. 继续手动修复（可能较复杂）
3. 调整设计稿以匹配实现

请选择下一步操作：
```

### 完成后

1. 汇总所有页面的对比结果和修复历史
2. 生成最终报告（修复成功/需用户决策）
3. 如有未解决问题，清晰列出供用户决策
